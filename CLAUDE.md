# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

TriSync is an Expo (SDK 54, React Native 0.81, React 19, new architecture enabled) app for planning race training (triathlon-style workouts: Swim, Bike, Run, Brick, Strength, Rest). It targets iOS, Android and web. Code is plain JavaScript (`.js`), even though `tsconfig.json` exists.

## Commands

- `npm start` — Expo dev server (`npm run ios` / `npm run android` / `npm run web` for a specific platform)
- `npx expo start -c` — restart with a cleared Metro cache; needed after changing `babel.config.js` or `tamagui.config.js`
- `npx expo install <pkg>` — add Expo-managed deps so versions match SDK 54

There are no build-time secrets. Each user enters their own Strava API app's Client ID and Secret in Settings → Strava, and they're stored on-device (`trisync/strava-keys/v1`). This makes every copy of the app its own instance. Never reintroduce `EXPO_PUBLIC_*` keys: Expo inlines them into the bundle.

- Production web build, as deployed: `EXPO_NO_DOTENV=1 EXPO_BASE_URL=/trisync npx expo export -p web --output-dir dist`

There is no test runner, linter, or formatter configured.

**Deploy:** `.github/workflows/deploy-web.yml` publishes the web build to GitHub Pages on every push to `master`. `app.config.js` applies `experiments.baseUrl` only when `EXPO_BASE_URL` is set, so local dev still serves from `/`. `public/` holds the PWA files: a customised `index.html` with manifest and home-screen tags, `manifest.json`, the icons, and a network-first `sw.js`. `index.js` registers the service worker on web in production only. `src/pwa/installPrompt.js` is imported early in `index.js` so it catches Chrome's one-time `beforeinstallprompt` event before React mounts. The ☰ menu's "Install TriSync" item replays that prompt, or opens `InstallModal` with per-platform steps (iOS never fires the event). The item is hidden when the app is already running installed. Paths in `public/` must stay relative, so they work under the `/trisync/` base path.

## Architecture

- **Entry:** `index.js` registers `App.js` and loads `app.web.css` only on web (it makes `#root` a full-height flex column so React Native Web scroll views work). `global.css` is not currently imported.
- **App shell (`App.js`):** `ThemeProvider` wraps everything. Once the Josefin Sans fonts load, it renders `TamaguiProvider` → `StravaProvider` → `TrainingProvider` → `NavigationContainer` with a bottom tab navigator holding two screens: `TodaysActivitiesScreen` ("Today") and `TrainingCalendarScreen` ("Calendar"). `HeaderLogo` (the tri glyph, tinted with `t.text`) is rendered as `headerLeft` and `TrainingHeaderMenu` as `headerRight` on every tab.
- **State (`src/training/TrainingContext.js`):** a single React context, accessed with `useTraining()`, holds every race plan: `plans` (`[{ id, raceName, raceDate, start, weeks, workouts }]`, sorted by race date) and `activePlanId`, saved to AsyncStorage (`trisync/training/v2`; localStorage on web). Screens work on the current plan through `planRange` (`{ start, raceDate, raceName, weeks }`, or `null` when there are no plans) and `workouts`, and the workout actions (`addWorkout`, `updateWorkout`, `deleteWorkout`) apply to it. `allWorkouts` spans every plan, so a Strava activity is never linked twice across plans. `normalizeTrainingData` converts older data: the single-plan `trisync/training/v1` shape, the pre-rename `oneplan/*` key, and old backup files. The provider renders a blank screen until the saved data has loaded, so the empty initial state never overwrites it. `createPlan` returns `{ error }` for validation failures. It clamps the plan start to today, but an edited plan that has already begun keeps its original start. The setup form on the Calendar tab opens for a first plan, for editing (`editingPlan`, pre-filled; the plan stays intact until saved or cancelled; opened from the pencil icon on a plan in My Plans, which makes that plan current first) and for "New plan" (`creatingPlan`). The ☰ menu's "My Plans" opens `PlansModal`, which lists upcoming and completed plans; tapping one makes it current (`selectPlan`), and plans can be deleted (`deletePlan`) after a confirmation.
- **Shared module (`src/training/trainingUtils.js`):** contains date helpers, workout types and icons, `statusFor()`, the `FONT_*` Josefin Sans family names, and `notesInputStyle(theme)`.
- **Theme (`src/theme/`):** `themes.js` defines the Dark palette (matching the Strava graphic), the Light palette and the Discord-style `GRADIENTS` presets. Gradient themes are built on a dark or light base, with translucent "glass" surfaces that are blurred on web. `ThemeContext.js` saves the user's choice (`trisync/appearance/v1`) and provides `useTheme()`, which returns colour tokens (`t.bg`, `t.surface`, `t.text`, `t.status.done`, ...), and `useAppearance()`, used by `SettingsModal` (opened from the ☰ menu). `AppBackground` draws the gradient behind the whole navigator with react-native-svg, so the header, scenes and tab bar are transparent in gradient themes. Components call `const t = useTheme()` and never hard-code colours. Menus and dialogs use `t.surfaceSolid`, because `t.surface` is see-through in gradient themes.
- **Shared UI (`src/training/WorkoutRow.js`):** exports `Pill`, `WorkoutRow` and `AddWorkoutForm`, which both screens reuse. A workout's heading adds an estimated distance (`Bike: 38 mins ≈ 11 miles`) from `estimateDistance` in `distanceEstimate.js`: the title's duration times a typical speed for the sport and the notes' `Intensity:` line (easy, steady or hard). Swims titled in metres are converted to yards in imperial instead. It's computed when displayed, never stored, and follows the Units setting (`appearance.units`, `'imperial'` by default, read with `useUnits()`). The ⋯ menu's "Swap or move" (`SwapPanel`) swaps a workout's day with another workout in the same plan week (weeks count from the plan's start, `planWeekDates`) or moves it to another day that week (`swapWorkouts`, `moveWorkout`). A brick's legs always move together. Workouts that are done, partial or linked to Strava can't be moved.
- **Strava (`src/strava/`):** `stravaApi.js` makes plain `fetch` calls to the Strava API (no backend). `StravaContext.js` keeps the user's API keys and OAuth session in AsyncStorage (`trisync/strava-keys/v1`, `trisync/strava/v1`), refreshes expired tokens, and exposes `syncWorkout`. The keys are passed into every `stravaApi` auth call. Changing the keys drops the session, because tokens belong to the app that issued them. `callbackDomain()` gives the value users must set as the Strava app's Authorization Callback Domain: `shahslab.github.io` on web (`WEB_CALLBACK_DOMAIN`; Strava always allows `localhost` too, so local dev works with the same setting). Settings explains Strava's per-app rate limit (100 requests every 15 minutes, 1,000 a day; a sync uses about 3), and a 429 response becomes a plain "limit reached" message. On web, login is a full-page redirect back to the app with `?code=`, which `StravaProvider` picks up on mount. On native it uses `expo-web-browser` with the `trisync://` scheme; that path is untested. When a workout is marked Done or Partial, `WorkoutRow` matches it to the Strava activity with the same date and sport. If there are zero or several candidates, the user picks one; for Brick workouts the user always picks, even when only one activity matches. Activities already linked to another workout are never offered again. The matched activity is stored on the workout as `stravaActivityId`. Its name becomes `TriSync: <workout title>`, falling back to Strava's own name. Its description is replaced with the workout notes; if the notes are empty, the description is left alone. A brick is entered as two Brick workouts on the same day, one per leg. Each leg's description gets the prefix `Brick Part N: `, where N comes from `brickPartFor`: the activity's position by Strava start time among the activities picked for that day's Brick workouts. When a leg syncs, legs synced earlier are renumbered (and rewritten only if their label changed). So once every leg is synced, the first leg is Part 1 whatever order the workouts were added or marked in, and other activities that day can't shift the numbers.
- **Activity graphic:** `activityGraphic.js` builds a 1080×1080 dark-card SVG string from the Strava activity's `laps`, or `splits_metric` if there's only one lap. It shows a headline distance (or time), the workout title and a status badge (green for Done, orange for Partial). The bars are about 32 slim bars, divided between laps by duration. Hard laps glow in the accent colour unless the effort was steady (speeds within 10%), in which case every bar lights. A progress line shows the share of time in hard laps, followed by a summary with highlighted numbers and a `TriSync · <plan week>` footer. `ActivityGraphicModal` previews the SVG and saves it: on web it draws it to a canvas and downloads a PNG; on native it uses `react-native-view-shot` and `expo-sharing` (untested). Strava's public API can't attach photos (partner apps only), so the user uploads the image to Strava manually.
- **Plan library (`src/plans/`, web only):** the new-plan form's "Available Plans" section (`PlanLibraryPicker`) offers 24 free triathlon plans (Sprint, Olympic, 70.3 and 140.6; Beginner, Intermediate and Advanced; 8 or 12 weeks). `src/plans/planLibrary.js` is the index and `public/plans/<id>.json` holds each plan's workouts (`{ week, day, type, title, notes }`, day 0 = the plan's first day); both are generated by `python3 scripts/build-plan-library.py "<folder of CSVs>"`, which also fixes the source files' typos, drops rest and race days and references to video guides that aren't included, and pairs "Run Off The Bike" with that day's ride as a Brick. A chosen plan is fetched on Create Plan and passed to `createPlan` as `template`, which places it so its last day is race day and rejects lengths that would start before today; the picker greys those out. Below it, "Import a Plan" (`PlanImportPicker`, `src/plans/planImport.js`) loads the same format from the user's own JSON file (`{ name?, weeks?, workouts }`; `weeks` defaults to the last week used), checks it with `parsePlanFile`, and passes it to `createPlan` as `template` too; it only shows while "None" is chosen in Available Plans, and picking a library plan drops the imported file. With no file, "None" is described as a blank plan.
- **Calendar export (`src/calendar/`, web only):** "Add to calendar" in the ☰ menu (current plan) and the calendar icon on each plan in My Plans open `CalendarExportModal`, which downloads the plan as an `.ics` file (`buildPlanIcs`: one all-day event per workout, plus race day; UIDs from workout ids) and explains importing into Google Calendar, Apple Calendar and Outlook. It's a one-off snapshot, not a live subscription, which would need a server.
- **Backup (`src/backup/backup.js`, web only):** Settings → Backup exports the training data, appearance and Strava API keys as a `trisync-backup-<date>.json` file, and imports one (replacing this device's data, then reloading). The Strava login session is deliberately left out, so users reconnect after an import. There is no server, so this is the only way to move data between browsers, devices, or Safari and an iPhone home-screen install. `index.js` also asks for persistent storage.
- **No zoom (web):** the viewport tag (`maximum-scale=1, user-scalable=no`) and `touch-action: pan-x pan-y` in `public/index.html`, plus `src/pwa/noZoom.js` (iOS pinch gestures, ctrl/⌘ + wheel or +/−/0), keep every screen at a fixed scale.
- `src/components/DashboardHeaderMenu.js` is unused. It is a leftover light/dark toggle.

## Conventions and gotchas

- **Dates:** dates are stored and compared as ISO `YYYY-MM-DD` strings (string comparison is used for ordering, e.g. in `statusFor`). User input and display use `DD-MM-YYYY`; convert with `displayToIso` and `isoToDisplay`. Helpers parse with a `T00:00:00` suffix (local midnight) and format back with `toIsoDate()`, which uses the local time zone. Never use `toISOString().slice(0, 10)`: it is UTC and shifts the date by a day in many time zones. For the same reason, don't use react-native-calendars' `minDate`/`maxDate`: it reads them as UTC midnight, which is off by a day in time zones behind UTC. Grey out days in the `dayComponent` instead, as the plan form's `RaceDatePicker` does.
- **Workout status:** the stored `status` is `'pending' | 'done' | 'partial'`. The displayed status comes from `statusFor(workout, today)`, which turns pending workouts into `'missed'` (past) or `'upcoming'`. In the calendar, a day with several workouts shows the worst status, ranked by `STATUS_PRIORITY`.
- **Styling:** styling mixes Tamagui layout primitives (`YStack`, `XStack`, `Card`, `Paragraph`, `$` tokens) with RN `Text`/`Pressable` and inline styles that use the tokens from `trainingUtils`. Popovers come from `@tamagui/popover`. Icons come from `@expo/vector-icons` (Ionicons).
- **Strava token requests** must be form-encoded, because `oauth/token` doesn't answer CORS preflights; a JSON body fails in the browser.
- **Fonts on Tamagui components:** `Paragraph`, `Input` and other Tamagui text components ignore a raw font name passed as the `fontFamily` prop (they only take `$` font tokens) and fall back to the system font. Pass it as `style={{ fontFamily: FONT_REGULAR }}` instead. RN `Text` and `TextInput` take it in `style` as usual.
- **Tamagui shorthands:** the app uses `@tamagui/config/v5`, whose shorthands differ from older Tamagui (`items`/`justify`, not `ai`/`jc`; `f` doesn't exist). Unknown shorthands are silently ignored, so use full prop names (`alignItems`, `justifyContent`, `flex`). `p`, `px`, `mt`, `mb` and `gap` are fine.
- **Inactive tabs on web:** `index.js` calls `enableScreens(true)` on web so inactive tab screens get `display: none`. Without it, bottom tabs just stack screens and rely on opaque backgrounds, so they show through each other in gradient themes.
- **Babel:** `babel.config.js` runs the Tamagui babel plugin and `react-native-reanimated/plugin`; the reanimated plugin must stay last.
